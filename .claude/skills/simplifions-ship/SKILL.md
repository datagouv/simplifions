Ships one Linear issue ([`simplifions-work` § Linear](../simplifions-work/SKILL.md#linear)): its plan, implementation, proof, review loop and pull request. The PR is the end: Thomas reviews, and the merge follows [`simplifions-work` § Human gates](../simplifions-work/SKILL.md#human-gates). GitHub is reached by `git push` and the PR's opening ([`simplifions-commit/pull-request.md`](../simplifions-commit/pull-request.md) § Opening it), nothing else.

## Usage
- `/simplifions-ship <issue>` - Ship that issue
- `/simplifions-ship` (no args) - Resume an in-progress ship ([`session.md`](session.md) § Resumption); none → report "No active ship session"

Progress lives in `.notes/<branch_name>/ship-session.md` ([`session.md`](session.md)). Update it after each phase change.

## Phases

1. **Setup** — read the issue at `.notes/sim-<n>-*/issue.md`; its folder gives the branch ([`simplifions-work` § Linear](../simplifions-work/SKILL.md#linear)). No such file: report that the user has not pasted the issue yet, and stop. A session file already there: set it `in-progress` and continue from its Phase (`session.md` § Resumption). Otherwise write it: status `in-progress`, phase `setup`. Locate the plan, `plan.md` in the same folder. It must exist with no unanswered questions, `Flag:` line or FIXME marker; otherwise mark the session `skipped` and stop. Switch to the branch, created from an up-to-date `origin/main` if needed (`git fetch`, then `git switch -c <branch> origin/main`, `CLAUDE.md` § Commits).
2. **Implement** — phase `implement`. Follow each plan step with the [red-green-commit](red-green-commit.md) cycle. Done when every plan step has its commit and the session's Plan step says so.
3. **Prove and push** — phase `push-pr`. Run the `/simplify` skill on the branch diff and apply its fixes; re-run tests, still green. Run `/accessibility:audit <file>` on every view or component created or modified (`CLAUDE.md` § Interface) and fix its blocking non-conformities. Then prove the change the way a user meets it, in a **fresh subagent** (`sonnet`: driving is mechanical, and a fresh context keeps each drive from replaying the whole ship). Its prompt opens with `Prove:`, then gives the checkout path, the feature map (`.claude/skills/simplifions-verify/`, its `SKILL.md` first), the feature the issue names and the behaviour to prove; it runs that feature's drive, `features/<feature>.rb`, in Chrome then Firefox, and returns the result lines and the evidence path. A feature the map does not cover gets its file and its drive in this PR first. A PR that changes how a feature is reached (a link, a label, a page, a step of the path) or what proves it (what the page shows, what the database holds) updates that feature file and its drive in the same PR, as the « Carte de vérif : … » commits in `git log` do. A `FAIL` comes back with what it saw: fix, then a new subagent; the third `FAIL` marks the session `blocked` with what the drive saw. No proof, no PR. Then the full suite (`docker compose exec web bundle exec rspec`) and `docker compose exec web bin/rubocop` green. Push with `git push -u origin <branch>`. Write the PR title and body (`simplifions-commit/pull-request.md`, its lines carrying the plan's « For the reviewer » items and what the drive showed, never the evidence path) under the session's `## Pull request`. Phase `review`.
4. **Review loop** — [`review-loop.md`](review-loop.md): fresh `/simplifions-review` subagent on the branch, triage, re-plan + re-ship, round cap 3. Done when a round has no open finding or the cap is hit.
5. **Hand over** — open the PR with the session's `## Pull request` title and body (`simplifions-commit/pull-request.md` § Opening it); then the report is one of [`output.md`](output.md)'s templates as written.
