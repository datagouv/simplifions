# Review

Read at phase 4 (review) of `/simplifions-ship`. One review, on the local branch, before the first push.

- Spawn a review subagent (fresh context, main model: review is judgment), in this checkout on the local branch, whose prompt is exactly:
  ```
  Run /simplifions-review — Ask: .notes/<branch_name>/issue.md
  ```
  The branch has no PR yet, so the issue file is how the reviewer finds the ask. Nothing else — the reviewer forms its own view from the branch; `/simplifions-review` carries the checklist and its passes. Save its report **verbatim** to `.notes/<branch_name>/review-report.md` (the `simplifions-review/output.md` shape, headings and numbering kept), then append `## Triage`, one line per triaged finding: `N. fixed | rebutted: <why> | deferred: <where> | open: <why>`.
- An **open finding** is one not yet fixed or rebutted, of any severity and any type but `pre-existing` (the findings the verdict counts); every open finding is fixed or left for Thomas. A `pre-existing` finding is not triaged.
  - **No open finding** → phase `push-pr`
  - **Open findings** → fix on the same branch:
    1. **Challenge each finding first.** A finding is a claim: its constat says the risk, its § Details line holds the proof in the fields of its type (`Reproduce:`, `Result:`, `Where:`…), and any direction is a way to go, never the fix (`simplifions-review/output.md`). A behaviour finding: start from its `Where:`, read its tests, then turn its `Reproduce:` steps into a failing test. It fails → the finding stands and that test is the red step. It passes, or the steps cannot be built → rebutted in `review-report.md` with what was tried. A finding on the ask (missing, deviates, unclear) is checked against the issue, not rebutted by a test: an unclear line is settled by a test or a drive that shows it. A design, simplicity, readability or `rule` finding (the last against its quoted rule) is checked by reading the code, then fixed without a red step, as a behaviour-preserving change; tests stay green. A design fix that reshapes more than the PR (a refactor of the system it fills), or a design finding that goes against a choice the plan states, is neither fixed nor rebutted: it goes in the PR body for Thomas, the plan line quoted.
    2. **Re-plan**: append a `## Review` section to `.notes/<branch_name>/plan.md` — same format and same one rule as /simplifions-plan ([`../simplifions-plan/one-rule.md`](../simplifions-plan/one-rule.md)): one step per standing finding, its failing test → fix, `remove <what>` alone for a removal, or `refactor <what>` for a behaviour-preserving fix; simplest fix only, flag rather than escalate. An **extra** the user wants kept is a scope change: ask the user, do not decide; a **missing** line is never rebutted, it is built or the issue is re-scoped by the user.
    3. **Fix**: implement the new steps with the `red-green-commit.md` cycle. A fix goes into the commit whose story it tells (`git commit --fixup <sha>`, squashed at phase 5 before the push) and into the file whose behaviour it covers, never into a file because its setup happens to make the test pass
- A finding the fixes leave open (its fix fails, or it goes against the plan's design or scope) is triaged `open`, and goes in the session's `## Notes` and under its `## Pull request` for Thomas, with whether you suspect the design or the scope. Thomas's review reads the fixes.
