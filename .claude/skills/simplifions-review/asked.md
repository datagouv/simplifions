# Asked versus built

Code review checks whether the change is sound; this pass checks whether it is the change that was asked for. A PR can pass every review round and still miss a behaviour the issue promised.

1. **Find the ask.** The issue as the user pasted it, `.notes/sim-<n>-*/issue.md` ([`simplifions-work` § Linear](../simplifions-work/SKILL.md#linear)): named in the prompt, or found from the SIM number of the PR body's `Closes` / `Suite de` link; and the brief `/simplifions-work` gave when there is one. The PR body itself is a claim to verify, never a source for the checklist. No issue and no brief → skip the pass and write `Ask: no source found` in the report. An issue with no file: a session the user talks to asks them to paste it; a subagent writes `Ask: not run — issue not pasted`, and the `Note:` says the change was not checked against its issue.
2. **Write the ask as a checklist** before reading the diff: every behaviour the issue promises, every limit it states (« does not », « stays »), every acceptance line. From the issue's words, not the plan's: the plan is the author's reading, the same one the diff came from.
3. **Read the diff against the checklist**, one mark per line: **delivered** (name the test or scenario that proves it), **missing** (nothing in the diff does it), **deviates** (done differently from what the issue says), **unclear** (the diff may cover it, say what would settle it). Then the reverse: **extra**: anything in the diff no line of the ask covers, with its size, and whether it crosses a stated limit.
4. **Check the user-facing lines.** When the diff touches routes, views or JavaScript, drive the mapped feature once with the feature map (`.claude/skills/simplifions-verify/`) on the branch's own checkout (no args, or `/simplifions-ship`'s loop) or on a worktree of the PR's branch (`bin/setup_worktree.sh`, then the verify map's first steps), and cite the evidence path; a feature the map does not cover gets a one-off drive (`simplifions-verify` § Drive). A line the review could not drive stays `delivered` when the code delivers it, and the report's `Note:` says the review could not check it: the review's limit, never a gap of the PR.
5. **Verdict**: `delivered` (every line delivered or proven, no deviation), `partial` (missing or unclear lines), `off-target` (a deviation, an extra that crosses a stated limit, or an extra larger than the ask). The verdict goes on the report's `Ask:` line. Each missing, deviating or unclear line and each limit-crossing extra is an `ask` row, ranked as `output.md` § Severity says; delivered lines stay off the report.
